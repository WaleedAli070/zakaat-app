# Zakaat App — Architecture Review v2 (2026-10-07)

Scope: review of `/Users/waleed.ali/work/zakaat-app/design_document.md` (v1.1) and the repo scaffold. All prices/limits below were fetched from the official page on 2026-10-07 unless marked SEARCH-ONLY or UNVERIFIED. Where a fact is derived rather than stated by the vendor, it is marked (inference).

## 0. Headline verdicts

1. The draft's security claims are not implementable as written: `auth.uid()` does not exist on Neon, "Supabase TDE" does not exist as a product, and Prisma `$use` middleware was removed in Prisma 7.
2. The hosting section contradicts itself (Lambda vs "Vercel or Cloudflare"). For this traffic shape (one burst per year), the cheapest honest answer is a single always-on container at $5–7/month or nothing at all (local-first).
3. For v1, the app does not need a backend for user data. All server-side needs (auth, prices, sync, backup) are either optional or satisfiable by a static daily price JSON plus iCloud/Google Drive backup. Recommendation: ship v1 local-first (Option 1), keep `packages/core` pure so Option 2 (cloud backend) can be added behind the same interface when multi-device sync becomes a real request.
4. If a backend is built, use Better Auth or Supabase Auth with Postgres on Neon, Drizzle not Prisma, a single container (Railway/Fly) or Cloud Run, and application-level scoping plus RLS as defence-in-depth via `set_config(..., true)` in a transaction — never `auth.uid()`.
5. Money must be `Decimal` end-to-end; `packages/core` currently uses `number`.

## A. AUTHENTICATION

### 1. Supabase Auth standalone vs alternatives
Verdict: it works but is the wrong shape for "DB on Neon". Supabase Auth stores its users in the Supabase project's own Postgres (`auth` schema), so a Neon-hosted app DB means two databases, two vendors, and a free-tier project that pauses after 7 days of inactivity — fatal for an app used once a year.

Facts:
- Supabase Auth: "You can use Supabase Auth as a standalone product" and "Auth uses your project's Postgres database under the hood" (https://supabase.com/docs/guides/auth). Free projects "are paused after 1 week of inactivity"; activity is defined as "sufficient user database activity" and whether auth-only traffic counts is not stated (https://supabase.com/docs/guides/platform/free-project-pausing). Free: 50,000 MAU; Pro from $25/mo incl. 100,000 MAU, then $0.00325/MAU (https://supabase.com/pricing). Native Apple via `expo-apple-authentication` ID token -> `signInWithIdToken` (https://supabase.com/docs/guides/auth/social-login/auth-apple); native Google via `@react-native-google-signin/google-signin` (https://supabase.com/docs/guides/auth/social-login/auth-google). Identity linking automatic by matching email; manual `linkIdentity()` off by default (https://supabase.com/docs/guides/auth/auth-identity-linking). Deletion: `auth.admin.deleteUser` requires service_role on a server (https://supabase.com/docs/reference/javascript/auth-admin-deleteuser). Refresh tokens single-use, 10 s reuse window, never expire; access JWT 1 h default (https://supabase.com/docs/guides/auth/sessions).
- Clerk: Free 50,000 MRU ("Monthly Retained Users"); Pro $25/mo ($20 annual) incl. 50k, then $0.02/MRU to 100k, $0.018 to 1M (https://clerk.com/pricing). `@clerk/clerk-expo` is deprecated in favour of `@clerk/expo` 4.8.1 (npm, 2026-10-07). Native Apple (iOS) and Google (iOS+Android) hooks exist, require a dev build, native components marked beta (https://clerk.com/docs/references/expo/overview). Self-delete via `user.delete()` gated by a dashboard flag. Passkeys via `@clerk/expo-passkeys` (https://clerk.com/docs/references/expo/passkeys).
- Firebase Auth: Spark free to 50k MAU; Identity Platform tier 1 $0.0055/MAU 50k–100k, $0.0046 100k–1M (https://cloud.google.com/identity-platform/pricing). Needs `@react-native-firebase/auth` 26.x with a dev build (not Expo Go) (https://rnfirebase.io/). Native Apple via `@invertase/react-native-apple-authentication`, Google via google-signin (https://rnfirebase.io/auth/social-auth). `deleteUser` requires recent sign-in.

- Better Auth: MIT, `better-auth` + `@better-auth/expo` 1.7.7 (2026-09-30). Expo plugin stores the session in expo-secure-store; `signIn.social({provider, idToken})` skips the browser for Apple/Google (https://www.better-auth.com/docs/authentication/apple, .../google). Account linking on by default; `deleteUser` opt-in with fresh-session check; any Postgres (pg/Kysely/Drizzle/Prisma), so it can live in the same Neon DB as the app (https://www.better-auth.com/docs/concepts/database). Magic-link, email-OTP and passkey plugins, the passkey plugin has an Expo section.
- AWS Cognito: Lite 10k free MAU then $0.0055; Essentials (default for new pools) 10k free then $0.015/MAU; Plus $0.02 (https://aws.amazon.com/cognito/pricing/). Amplify RN requires `expo prebuild`; social sign-in is `signInWithRedirect` (browser) with no documented native ID-token path (https://docs.amplify.aws/react-native/build-a-backend/auth/concepts/external-identity-providers/). Linking via `AdminLinkProviderForUser` (max 5 identities).

Token/session model for mobile (any provider): short-lived access JWT (5–60 min) in memory, refresh token in `expo-secure-store` with `WHEN_UNLOCKED_THIS_DEVICE_ONLY`; values should stay under ~2 KB ("Historically, some iOS releases refused values above roughly 2048 bytes", https://docs.expo.dev/versions/v54.0.0/sdk/securestore/) — store the refresh token, not the whole session blob.

### 2. Apple Guideline 4.8 (verified 2026-06-08 revision)
Yes. "Apps that use a third-party or social login service (such as Facebook Login, Google Sign-In, ...) to set up or authenticate the user's primary account with the app must also offer as an equivalent option another login service" that limits data to name and email, lets users keep their email private, and does not collect app interactions for advertising without consent. Exemptions: exclusively your own account system; alternative marketplace; education/enterprise; government eID; client for a specific third-party service. (https://developer.apple.com/app-store/review/guidelines/). Sign in with Apple satisfies this; so would passkeys or email magic-link in principle (they meet the three bullet criteria), but Sign in with Apple is the zero-argument path on iOS. `expo-apple-authentication` is iOS/tvOS only — "It does not yet support Android or web" (https://docs.expo.dev/versions/v54.0.0/sdk/apple-authentication/); on Android Supabase/Better Auth fall back to Apple's web OAuth in a browser.

Also directly relevant: 5.1.1(v) "If your app doesn't include significant account-based features, let people use it without a login. If your app supports account creation, you must also offer account deletion within the app." A calculator that forces Google/Apple sign-in before the user can compute anything is a 5.1.1(v) rejection risk; the local-first design side-steps it. Account deletion help page adds: deactivation is insufficient; Sign in with Apple apps "should use the Sign in with Apple REST API to revoke user tokens" (https://developer.apple.com/help/app-review/guideline-reference/5-1-1-account-deletion).

### 3. Email magic-link / passkeys and non-GMS devices
Facts: StatCounter mobile vendor share Sep 2026: Huawei 1.67 % Pakistan, 1.31 % UAE, 1.87 % Saudi Arabia (Honor, now GMS-capable, 0.47 / 5.07 / 5.65 %) (https://gs.statcounter.com/vendor-market-share/mobile/pakistan etc.). Google Play services "devices without Google Play services installed, aren't supported" (https://developers.google.com/android/guides/overview); Google-account login on non-GMS Huawei is reported impossible in third-party sources only (SEARCH-ONLY).
Verdict: Huawei is ~1.5–2 % of the market and shrinking; not worth HMS Account Kit work. But a non-OAuth path is still needed for (a) users who refuse Google/Apple, (b) 5.1.1(v), (c) Apple 4.8 equivalence on Android. Email OTP (6-digit code) is better than magic link on mobile because deep-link return is brittle; Supabase, Clerk, Better Auth (email-otp plugin) and Cognito Essentials all support it. Passkeys are nice-to-have for v2 (Clerk and Better Auth have Expo support; Cognito Essentials too). In the local-first design the answer is simpler: no account at all; optional cloud backup uses the platform's own identity (iCloud / Google Drive appData).

### 4. Verifying the IdP JWT in NestJS and passing the user id to Postgres
Pattern: `jose` 6.x `createRemoteJWKSet(new URL(jwksUrl))` + `jwtVerify(token, jwks, { issuer, audience, algorithms })`, cached per process; a Nest guard puts `sub` on the request; the repository layer opens a transaction and runs `SELECT set_config('app.user_id', $1, true)` before queries (see 5).
Claims per provider: Supabase — JWKS `https://<ref>.supabase.co/auth/v1/.well-known/jwks.json` (asymmetric keys since July 2025), `iss = https://<ref>.supabase.co/auth/v1`, `aud = "authenticated"`, `sub` = user UUID, `role` (https://supabase.com/docs/guides/auth/signing-keys, .../jwt-fields). Clerk — JWKS at Frontend API `/.well-known/jwks.json`, check `exp`, `nbf`, `iss`, `azp` against known origins; no `aud` by default (https://clerk.com/docs/backend-requests/manual-jwt). Firebase — x509 certs at `securetoken@system.gserviceaccount.com`, `aud` = project id, `iss = https://securetoken.google.com/<projectId>` (https://firebase.google.com/docs/auth/admin/verify-id-tokens). Cognito — `https://cognito-idp.<region>.amazonaws.com/<poolId>/.well-known/jwks.json`, `token_use`, `aud`/`client_id` (https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-tokens-verifying-a-jwt.html). Better Auth — session cookie/bearer validated by the library itself in-process, no JWKS needed unless you enable its `jwt` plugin.
Note: docs.nestjs.com/security/authentication now documents a new `@nestjs/authentication` package (npm 0.0.1, 2026-09-29) with a `JwtBearerProvider`; it is too new to depend on — use `jose` directly.

## B. DATABASE, RLS, ENCRYPTION

### 5. RLS with Prisma, PgBouncer/Neon pooler, `auth.uid()`
Confirmed: `auth.uid()` is defined by Supabase's own migrations as `select nullif(current_setting('request.jwt.claim.sub', true), '')::uuid` in the `auth` schema (https://github.com/supabase/postgres/blob/develop/migrations/db/init-scripts/00000000000001-auth-schema.sql). It does not exist on vanilla Postgres or Neon. Neon's `pg_session_jwt` extension exposes `auth.user_id()`/`auth.uid()` but "is automatically installed when you enable the Neon Data API ... Do not install this extension manually" and is designed for the Data API (JWT-per-request over HTTP), not for a Prisma TCP connection (https://neon.com/docs/extensions/pg_session_jwt, https://neon.com/docs/data-api/access-control). The old "Neon Authorize/Neon RLS" guide URLs now 404 or redirect to the Data API pages (status UNVERIFIED — no deprecation notice found).

Working pattern with Prisma (official example): a client extension that wraps every operation in a batch `$transaction` whose first statement is `` $executeRaw`SELECT set_config('app.user_id', ${userId}, TRUE)` `` (https://github.com/prisma/prisma-client-extensions/tree/main/row-level-security). Policy: `USING (user_id = current_setting('app.user_id', true)::uuid)`. The app role must be `NOBYPASSRLS` and not the table owner (owners bypass RLS unless `FORCE ROW LEVEL SECURITY`).
Pitfalls:
- Pooling: Neon's pooler is PgBouncer in transaction mode; "SET/RESET (session variables)" are unsupported on the pooled endpoint (https://neon.com/docs/connect/connection-pooling; PgBouncer matrix https://www.pgbouncer.org/features.html). `set_config(..., true)` / `SET LOCAL` inside an explicit transaction is scoped to that transaction, and in transaction mode the connection is pinned for the transaction, so it is safe (inference from the two docs; neither vendor states it in one sentence). Session-level `SET` leaks to other tenants' requests — the classic cross-tenant bug.
- The Prisma example's own caveat: because every call becomes a batch transaction, your own `$transaction` calls "may not work as intended". Interactive transactions must carry the `set_config` themselves.
- `?pgbouncer=true`: Prisma now says "We recommend not setting pgbouncer=true ... if you're using PgBouncer 1.21.0 or later" (https://www.prisma.io/docs/orm/prisma-client/setup-and-configuration/databases-connections/pgbouncer); Neon's Prisma guide uses the `-pooler` host plus `DATABASE_URL_UNPOOLED` for migrations and never mentions the flag (https://neon.com/docs/guides/prisma). Drop it from the doc.
- Prisma 7 removed `$use` middleware and requires a driver adapter (https://www.prisma.io/docs/orm/more/upgrade-guides/upgrading-versions/upgrading-to-prisma-7).
- With Drizzle, the same thing is `db.transaction(async tx => { await tx.execute(sql\`select set_config('app.user_id', ${id}, true)\`); ... })`; Neon documents a `crudPolicy` helper for Drizzle (https://neon.com/docs/guides/row-level-security).

Is RLS worth it? For a single application role with a solo developer, RLS is defence-in-depth, not the primary control; a tested repository layer that takes `userId` as a mandatory argument (and a lint rule that forbids raw `prisma.asset.findMany` outside it) prevents the same class of bug. RLS adds: protection against a forgotten `where`, and against any future direct-DB tool (Data API, admin scripts). It costs: an extra round-trip per request, a trap with pooling, and harder debugging.
Recommendation: application-level scoping as the primary mechanism with integration tests that assert cross-tenant reads return zero rows; enable RLS as a second layer only once there is more than one way to reach the DB. If you go Supabase-all-in, RLS is mandatory because the client talks to Postgres directly.

### 7. Encryption
What the vendors actually offer: Neon — AES-256 on NVMe storage, keys in AWS KMS/Azure Key Vault, TLS in transit (https://neon.com/docs/security/security-overview). Supabase — "All customer data is encrypted at rest with AES-256", TLS in transit; no TDE product (https://supabase.com/security). Supabase explicitly says pgsodium transparent column encryption "will be deprecated" and does "not recommend" TCE/SKM "due to their high level of operational complexity and misconfiguration risk" (https://supabase.com/docs/guides/database/extensions/pgsodium); Vault is for secrets, not user columns (https://supabase.com/docs/guides/database/vault). So "ensure Supabase TDE is active" is not an action anyone can take; disk encryption is on by default and protects against stolen disks, not against a leaked connection string, a SQL-injection, a compromised admin account, or the vendor itself.

Options for real protection:
- pgcrypto: Postgres itself warns "all the data and passwords move between pgcrypto and client applications in clear text ... If you cannot [trust the DBA], then better do crypto inside client application" (https://www.postgresql.org/docs/current/pgcrypto.html). Keys appear in SQL text and logs. Not recommended.
- App-side AES-256-GCM with envelope encryption: a per-user data key (DEK) encrypted by a master key (KEK) in AWS KMS ($1/key/month, $0.03 per 10k requests, 20k free/month, https://aws.amazon.com/kms/pricing/) or a KEK in the secret store with the DEK cached per request. Protects against DB-level leaks; does not protect against a compromised API server. Breaks server-side SUM/ORDER BY on the encrypted columns — totals must be computed in the API after decryption (fine at this data size).
- `prisma-field-encryption`: latest stable 1.6.0 (2024-09-24), beta 1.6.1-beta.2 (2026-01-27); README "requires Prisma 4.7.0 up to 6.13.0", "You can only encrypt String fields" (not Decimal), Prisma 7 issues (#148, #149, #153) closed as duplicates with no supporting release (https://github.com/47ng/prisma-field-encryption). Not usable with Prisma 7/8 and cannot encrypt the `Decimal` columns the draft wants to protect.
- Client-side (on-device) encryption: server stores ciphertext it cannot read; key derived on device and backed up via iCloud Keychain/Google Drive. Trade-off: the server cannot compute totals, run analytics, or send "you owe X" notifications; every calculation runs on-device in `packages/core`. This is exactly the local-first design in 19.

Recommendation for a solo/small team: do not build server-side field encryption in v1. Either (a) keep the data on-device (Option 1) where the OS data-protection class (`NSFileProtectionComplete` / Android file-based encryption) plus optional SQLCipher is the control, or (b) in Option 2 use app-side AES-256-GCM with a per-user DEK for the few numeric columns (`cash_value`, `amount`, `weight_grams` stored as encrypted strings; keep a coarse, unencrypted `band` column if you ever need aggregate stats). Skip KMS until you have a second engineer; a KEK in the platform secret store rotated annually is proportionate.

### 8. Prisma vs Drizzle (2026)
Facts: Prisma 7.0.0 shipped 2025-11-19 with the Rust-free TypeScript client as default — "90% smaller bundle size (from ~14MB to 1.6 MB)", "up to 3.4x faster queries" (https://www.prisma.io/blog/prisma-orm-without-rust-latest-performance-benchmarks, https://www.prisma.io/blog/rust-free-prisma-orm-is-ready-for-production); driver adapters mandatory (`@prisma/adapter-neon` over WebSockets or `@prisma/adapter-pg`), `prisma.config.ts`, `$use` removed. Prisma 8 is tagged `latest` on npm as 8.0.0-rc.20 (2026-10-05) and the docs call it "the current release" while the blog says final is "four to eight weeks out" from Sept 2026 — in other words, the repo's Prisma 5.22 is two majors behind and the target is moving. `Decimal` maps to decimal.js (https://www.prisma.io/docs/orm/prisma-client/special-fields-and-types). No official Lambda cold-start ms for Prisma 7/8 (UNVERIFIED).
Drizzle: `drizzle-orm` 0.45.3 (2026-09-21), 1.0.0-rc.4; zero runtime dependencies; `neon-http` driver for single-shot queries, `neon-serverless` (WebSocket) for interactive transactions (https://orm.drizzle.team/docs/connect-neon); `numeric({ mode: 'string' | 'number' | 'bigint' })`, default `'string'` (https://orm.drizzle.team/docs/column-types/pg) — wrap in decimal.js yourself. Neon's own guidance: Drizzle's "runtime stays small ... which matters on serverless hosts" (https://neon.com/guides/prisma-drizzle-typeorm-postgres). Drizzle also has an `expo-sqlite` driver and migrations runner (https://orm.drizzle.team/docs/connect-expo-sqlite), so one query builder can serve the device DB and the server DB.
Recommendation: Drizzle. The deciding factor is not Lambda size (Prisma 7 closed most of that gap) but that Drizzle runs on-device with expo-sqlite, has a stable API while Prisma is mid-major-transition, and is explicit about transactions, which matters for the `set_config` RLS pattern. If you stay on Prisma, go straight to 7.x with `@prisma/adapter-neon`, never 5.22.

Compute cost is therefore ~$0 everywhere; what differs is the fixed floor, cold-start experience, and ops burden.

### 15. Hijri calendar handling
Facts: Hermes uses platform Intl ("Android and iOS platform provided facilities", https://github.com/facebook/hermes/blob/main/doc/IntlAPIs.md). The `calendar` option is read and passed through on both platforms: iOS `PlatformIntlApple.mm` sets `NSCalendar initWithCalendarIdentifier:` from the option string; Android `PlatformDateTimeFormatterICU.java` sets the `ca` locale extension and uses `android.icu.util.Calendar` (sources on facebook/hermes main). Android's ICU `IslamicCalendar` with `islamic-umalqura` exists since API 24 (https://developer.android.com/reference/android/icu/util/IslamicCalendar); Apple's `islamicUmmAlQura` identifier since iOS 8. However Hermes issue #1716 ("resolvedOptions().calendar is undefined" on iOS) was only fixed by PR #2183 merged 2026-10-05 — after SDK 54/57 — so on current releases you cannot introspect which calendar was applied, and the Hermes doc warns Android <24 has "issues with the calendar configuration" and results "may vary between devices". No runtime evidence that `islamic-umalqura` formatting is correct on Hermes was found (UNVERIFIED). Temporal is Stage 4 and ships in Firefox 139, Chrome 144, Node 26 but not Safari/JSC/Hermes; `@js-temporal/polyfill` 0.5.1 is 128 KB ESM and marked alpha; Firefox disables islamic calendars in `withCalendar()`. Libraries: `moment-hijri` 3.0.0 (2024-10-31, 35k dl/wk, needs moment), `@umalqura/core` 0.0.7 (2019, 13.5k dl/wk, zero deps), `hijri-converter` 1.1.1 (2018), `hijri-date`/`hijri-js` (2017) (npm registry). Aladhan `gToH` API: methods HJCoSA (Umm al-Qura adjusted for Saudi sighting announcements), UAQ, DIYANET, MATHEMATICAL (+/- day adjustment); 12 req/s rate limit, no quota text; no Pakistan-sighting method (https://api.aladhan.com/v1/documentation/openapi/islamic-calendar/yaml).
Umm al-Qura vs sighting: Umm al-Qura is "a calculated lunar calendar" used by Saudi Arabia and followed in Bahrain, Qatar, UAE; actual first sighting "can occur up to two days after the date predicted" and observed dates across communities "differ by one, two or even three days" (van Gent, https://webspace.science.uu.nl/~gent0113/islam/ummalqura_introduction.htm; Aladhan method notes). Pakistan's months start on the Ruet-e-Hilal Committee's witness-based announcement (Wikipedia).
Recommendation: do not rely on `Intl.DateTimeFormat(..., {calendar: 'islamic-umalqura'})` for anything that affects money. Put a pure, tested Umm al-Qura conversion in `packages/core` (vendor the ~190 KB `@umalqura/core` table or port the Kuwaiti algorithm — it is a few hundred lines and the tables are static through 1500 AH), use it to compute the hawl anniversary, and expose a per-user `hijriOffsetDays` (-2..+2) the user can set when their local announcement differs. Store both `hawl_start_gregorian` and `hawl_start_hijri` plus the offset in the period row. Use `Intl` only for display, and only after a device test on iOS and Android <24.

### 17. App Store and Google Play review considerations
Apple (guidelines "Last Updated: June 8, 2026", https://developer.apple.com/app-store/review/guidelines/):
- 1.1.1 forbids "defamatory, discriminatory, or mean-spirited ... commentary about religion"; a devotional calculator with sourced fiqh rulings is not that. Avoid editorialising between madhhabs in-app copy.
- 3.2.1(viii): "Apps used for financial trading, investing, or money management should be submitted by the financial institution performing such services and must have necessary licensing". A zakat calculator does not perform money management for the user (no accounts, no transfers), but the phrase "personal finance tracker" in your store listing invites this clause. Describe it as a "zakat calculator and record keeper"; never add bank connections to a non-institution app.
- 5.1.1(ix): apps "in highly regulated fields (such as banking and financial services ...) or that require sensitive user information should be submitted by a legal entity ... and not by an individual developer". Again the listing wording decides whether a reviewer reaches for this; see 18.
- 5.1.1(v): account deletion in-app if you have accounts; no login wall if the app "doesn't include significant account-based features".
- Privacy nutrition label: "Other Financial Info: Such as salary, income, assets, debts" must be declared only if "collected", which Apple defines as "transmitting data off the device" (https://developer.apple.com/app-store/app-privacy-details/). A local-first app with optional iCloud backup declares nothing in this category; the cloud design declares Financial Info linked to identity.
- 3.1.1 IAP for any paid tier (subscriptions/unlocks); "tips" allowed via IAP.
- Charities: 3.2.2(iv) "Unless you are an approved nonprofit or otherwise permitted under 3.2.1(vi), collecting funds within the app for charities and fundraisers [is not permitted]. Apps that seek to raise money for such causes must be free on the App Store and may only collect funds outside of the app, such as via Safari or SMS." 3.2.1(vi) lets approved nonprofits fundraise with Apple Pay. Linking out to a charity's website is fine; an in-app "pay your zakat here" button that takes money is not, unless the charity is Apple-approved and the money goes to it directly.
Google Play:
- Data safety: "Other financial info: Any other financial information such as user salary or debts"; collection means transmitted off device (https://support.google.com/googleplay/android-developer/answer/10787469).
- Financial Services policy scope is "products and services related to the management or investment of money and cryptocurrencies, including personalized advice"; its sections are binary options, personal loans, earned wage access, plus country-specific loan rules (Pakistan listed) (https://support.google.com/googleplay/android-developer/answer/9876821). A zakat calculator is not a loan or EWA app. However the Financial Features Declaration is mandatory for every app; its category list has no "budgeting/calculator" entry, so select "My app doesn't provide any financial features" and keep the listing consistent with that (https://support.google.com/googleplay/android-developer/answer/13849271).
- Target API: new apps and updates must target Android 16 / API 36 since 2026-08-31 (extension to 2026-11-01 on request) (https://support.google.com/googleplay/android-developer/answer/11926878). Confirm the `targetSdkVersion` of whichever SDK you ship on against this deadline.
- Personal developer accounts created after 2023-11-13 must run a closed test with "a minimum of 12 testers who have been opted in continuously for at least 14 days" before applying for production; review "usually takes seven days or less" (https://support.google.com/googleplay/android-developer/answer/14151465). The "20 testers" figure in the question is stale; it is 12.
- Android developer verification for sideloading starts 2026-09-30 in Brazil/Indonesia/Singapore/Thailand and goes global in 2027 (https://developer.android.com/developer-verification).
Recommendation: position as a calculator/record keeper, not a finance app; never collect money in-app; link out for charity payments; declare "no financial features" on Play; start the 12-tester closed test the day you have a build.

Backup primitives: iCloud KVS is 1 MB/1,024 keys (too small for history, fine for a key); `react-native-cloud-storage` 3.1.1 (2026-10-02) gives iCloud Documents + Google Drive appData with an Expo plugin (https://github.com/kuatsu/react-native-cloud-storage); Drive appData files are hidden from the user and deleted on uninstall (https://developers.google.com/workspace/drive/api/guides/appdata); `expo-file-system` + `expo-sharing` cover a manual encrypted export.

Honest evaluation for this app: the data is a few hundred rows per user, written a dozen times a year, read once a year. There is no collaboration, no server-side computation the device cannot do (prices are public data), and no feature that needs a server to know the user's numbers. A backend therefore adds cost, a privacy-label obligation, a login wall (5.1.1(v) risk), GDPR controller duties, and a breach surface — for the sole benefit of multi-device sync, which is a v2 request at best.
Is a backend needed in v1? No. What is needed server-side: (a) a daily price/FX JSON on a CDN (no auth, no user data), (b) optional backup, which iCloud Documents / Google Drive appData give you without your own server and without an account of your own.
Trade-offs you accept: no cross-device sync (mitigate: backup/restore via the user's cloud drive; for a household, an export file); no server-sent notifications (local scheduled notifications cover "hawl ends in 10 days", see 20); price snapshot integrity depends on the device having fetched a signed/published daily file — mitigate by shipping the price JSON with an Ed25519 signature from the publishing job and storing the fetched file hash in the calculation snapshot, and by bundling the last 30 days of prices in the app binary as a fallback; analytics are opt-in and amount-free.
Recommendation: build v1 local-first (expo-sqlite + Drizzle + `packages/core` on device, SQLCipher on, iCloud/Drive backup, static daily price JSON). Keep the repository interface in `packages/core` storage-agnostic so Option 2's server can be added behind it. If multi-device becomes real demand, the least-work upgrade is Turso embedded sync (Developer $4.99/mo) on top of the same SQLite schema, not a REST rewrite; PowerSync works too but its free tier deactivates after one idle week and Pro is $49/mo.

## E. ACCOUNTING / MONEY CORRECTNESS

### 22. Storing money and precision
Verdict: NUMERIC in Postgres, decimal.js in TS everywhere money or weight is touched; never `number`. The draft already uses `@db.Decimal(15,2)` but `packages/core/index.ts` takes `number` for weight and price, so the engine would compute in IEEE-754 floats and only the storage would be exact.

- Postgres: "Calculations with numeric values yield exact results where possible ... If you require exact storage and calculations (such as for monetary amounts), use the numeric type instead." Rounding differs: "the numeric type rounds ties away from zero, while ... real and double precision types round ties to the nearest even number." https://www.postgresql.org/docs/current/datatype-numeric.html (VERIFIED-FETCHED)
- Integer minor units vs NUMERIC: integer minor units (e.g. PKR paisa as BIGINT) are the usual recommendation for single-currency ledgers, but this app stores 7 currencies with different exponents and non-money quantities (grams, purity fractions, FX rates with 4-6 decimals, prices per gram). A single `NUMERIC(20,6)` for amounts plus a `currency` column, and `NUMERIC(12,4)` grams, is simpler and loses nothing. Prisma `Decimal` maps to decimal.js (`Prisma.Decimal` is a decimal.js instance), so the same arithmetic library runs on server and client. decimal.js 10.6.0 (last publish 2025-07), ~284 KB unpacked (npm registry metadata, VERIFIED via `npm view`).
- Rounding rule: the doc says "always round UP" for the zakat due. That is a defensible fiqh choice (err in favour of the recipient) but must be (a) applied once, at the final `due` figure, never on intermediate lines, and (b) stored as a named rule in the explanation (`ROUND_UP_TO_MINOR_UNIT`). Use `Decimal.ROUND_UP` (away from zero) or `ROUND_CEIL`; for display of intermediate values use `ROUND_HALF_EVEN`. Never rely on Postgres `round()` for the final figure because its tie-handling (away from zero) differs from JS `Math.round` (toward +inf) and from decimal.js defaults (ROUND_HALF_UP).
- 2.5 %: compute as `wealth.mul('0.025')` or `wealth.div(40)` in decimal.js; never `* 0.025` in floats. Both are exact in decimal arithmetic.
- Gold: store `weight_grams NUMERIC(12,4)` (0.1 mg resolution covers tola 11.6638 g, masha, ratti conversions), `purity` as an exact fraction `karat/24` -> store `karat SMALLINT` and derive, or `purity_permille SMALLINT` (916, 750, 999). Do not store purity as a float.
- Valuation snapshot: every valuation row records `original_amount, original_currency, fx_rate, fx_rate_source, fx_rate_date, metal_price_per_gram, metal_price_source, metal_price_date, base_currency, base_amount`. Rows are immutable; a re-valuation inserts a new row. This is the only way "what did I owe on 17 Ramadan 1447" stays reproducible after prices move.

### 23. Ledger design: obligation vs payments
Verdict: model as an append-only journal with period (hawl) headers; the draft's `ZakaatPeriod.totalDue` mutable column plus mutable `Payment` rows will not survive the first "I entered the wrong amount last year" support ticket.

Recommended shape:
- `hawl_period` (id, user_id, start_hijri, start_gregorian, end_hijri, end_gregorian, status ENUM(open, closed, reopened), closed_at, calculation_snapshot_id, carried_in NUMERIC, carried_out NUMERIC).
- `calculation_snapshot` (id, period_id, engine_version, ruleset_id, madhhab, inputs JSONB (frozen copies of every asset/liability row as valued), prices JSONB (every price and FX rate used, with source and date), outputs JSONB, explanation JSONB (see 24), created_at). Immutable. A period can have many snapshots (previews); exactly one is marked `authoritative` when the period closes.
- `ledger_entry` (id, user_id, period_id, seq BIGSERIAL, kind ENUM(obligation, payment, adjustment, reversal, carry_forward), amount NUMERIC(20,6) signed, currency, payment_category (masarif), recipient, occurred_at, recorded_at, reverses_entry_id NULL, note). Append-only: UPDATE/DELETE revoked from the application role; corrections are a `reversal` row that references the original, plus a new row.
- Balance for a period = SUM(obligation) + SUM(carry_forward in) - SUM(payment) +/- adjustments. Compute with a view, cache nothing writable.
- Close: closing a period freezes the authoritative snapshot and writes the `obligation` entry; if balance != 0 at close, write a `carry_forward` out of this period and a matching `carry_forward` into the next one (overpayment carried as negative obligation / advance zakat; shortfall carried as outstanding). Fiqh note: advance payment of zakat is held permissible by the majority view (confirm with your reviewing scholar), so carrying an overpayment forward is defensible, but the UI should state it and let the user choose "treat as sadaqah" instead.
- Reopen: do not unlock rows. `reopened` state allows new entries referencing the period; the original snapshot remains, a new authoritative snapshot is produced and both are kept with `superseded_by`.
- Engine versioning: `packages/core` exports `ENGINE_VERSION` (semver) and a `ruleset` id (e.g. `hanafi@2026.1`). The snapshot stores both plus the full inputs; a test asserts that replaying `inputs` through `ruleset` at `engine_version` reproduces `outputs` byte-for-byte. Keep old rulesets importable (`rulesets/hanafi/2026.1.ts`) rather than mutating in place.

### 24. Explainability / audit trail
Verdict: the draft's `auditTrail: ["Gold taxed per Hanafi rule"]` (free strings) is the wrong shape; strings cannot be localised (Urdu/Arabic), tested, or diffed.

Structured explanation entry (TypeScript shape to put in `packages/core`):
```
type Explanation = {
  ruleId: string;            // "JEWELLERY_ZAKATABLE", "DEBT_DEDUCTION_12M", "NISAB_SILVER_612_36G"
  madhhab: 'HANAFI'|'SHAFII'|'MALIKI'|'HANBALI'|'GENERAL';
  subjectId: string;         // asset or liability id
  inputs: Record<string, string>;   // decimal strings, never numbers
  output: string;            // decimal string
  effect: 'INCLUDE'|'EXCLUDE'|'DEDUCT'|'PARTIAL'|'INFO';
  citation?: { source: string; ref: string; url?: string }; // e.g. AAOIFI Shari'ah Standard 35, Fiqh Academy resolution
  messageKey: string;        // i18n key; UI renders text
  severity: 'info'|'warning';
}
```
Emit one entry per rule application; the UI's "Why am I being taxed?" renders `messageKey` with `inputs` interpolated. Store the array in `calculation_snapshot.explanation`. Because rules are identified by id, golden tests (25) assert on `ruleId` sequences, not on prose.

### 25. Testing the fiqh rules engine
Verdict: three layers, with scholar-signed golden vectors as the contract.
1. Golden vectors: `packages/core/test/vectors/<madhhab>/<case>.json` with `{inputs, prices, expected: {due, explanations[ruleId...]}, reviewedBy, reviewedOn, signature}`. One vector per rule row in the design doc table (jewellery, debt deduction, retirement net value, passive stocks 25 %, plot files, hawl dip) x madhhab = ~28 base vectors, plus edge cases (exactly at nisab, zero assets, debt > assets, multi-currency, purity 18/21/22/24k). Have the reviewing scholar sign the JSON (detached GPG signature or just a committed `reviewedBy` block) so a diff to a vector is visibly a fiqh decision, not a code change.
2. Property-based tests with fast-check (4.10.2, published 2026-09, `npm view`): invariants such as due >= 0; due == 0 iff net wealth < nisab; due is monotone non-decreasing in zakatable assets; changing base currency and converting back yields the same due within 1 minor unit; engine(inputs) is deterministic and pure (same inputs, same output); GENERAL mode due >= min(due across madhhabs) (the "safe" mode never undercuts).
3. Snapshot tests of the full `Explanation[]` for each golden vector so an accidental rule reorder or message change is caught.
4. Replay test: for every stored `calculation_snapshot` fixture, replay through the pinned engine version and compare.
Tooling: vitest in `packages/core`, run on every PR; vectors are data, so non-engineers (the scholar) can read them.
